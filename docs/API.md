# API contract

**Status: Draft. Changes to this file or to `proto/findings.proto` need an ADR** (see [decisions/0001-grpc-instead-of-rest.md](decisions/0001-grpc-instead-of-rest.md)).

Services talk over gRPC. Messages are described once in `proto/findings.proto` (package `quantumshift.v1`), and code for C++, Java and Python is generated from it.

## The `Finding` message

| Field | Type | # | Meaning |
|---|---|---|---|
| `location` | string | 1 | File path and line, or binary offset |
| `algorithm` | string | 2 | For example `RSA`, `ECDSA-P256`, `AES-256` |
| `purpose` | string | 3 | One of `key_exchange`, `signature`, `encryption`, `hashing` |
| `vulnerable` | bool | 4 | Breakable by a quantum computer? |
| `confidence` | float | 5 | 0.0 to 1.0 |
| `evidence` | string | 6 | Why we think so |

## Service calls (draft)

Grounded in the project plan. Only `Finding` is defined in the proto so far.

| Caller | Callee | Call | Returns | Plan section |
|---|---|---|---|---|
| Java orchestrator | C++ scanner | `ScanBinary(file)` | Findings for the binary | 4.2 |
| Java orchestrator | Python classifier | Classify the source files of a project (exact request shape undecided) | Findings: algorithm, purpose, quantum-vulnerable, confidence, evidence | 4.1, 5.3 |

Candidate extraction (tree-sitter, stage 1) happens inside the classifier, not in the orchestrator, so the orchestrator does not send individual snippets (plan 4.1 and Section 6, step 1).

Not gRPC calls:
- The Java config and certificate parser (plan 5.4) is not defined as a gRPC service in the plan, so no call is documented for it. Whether it is a separate service is a Phase 1 decision.
- The RAG planner reads benchmark numbers directly from PostgreSQL. They are given to the LLM as a table and never generated by it (plan 5.8).

## Open items

Request and response message shapes beyond `Finding` are not decided. Defining them (and the service definitions in the proto) is the first ADR task in Phase 1, agreed in week 1 so the six members can work in parallel.
